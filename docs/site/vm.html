ESPlab runs user work as sandboxed bytecode tasks. You write a small assembly program, assemble it to ESPlab bytecode (vbasm), and submit it to the cluster. The cluster splits the work into chunks; every board in the cluster executes the same task on its own slice of the input, and the results come back to the coordinator. One program, every chip — the bytecode is identical on an ESP32, an S3, a C3, or the virtual boards.

This page documents the VM itself. For the cluster around it — election, scheduling, storage — see the main repo.

1. The mental model

A task is a function over a slice. The machine gives your task:

  • input — the same bytes for every chunk of a job (a search predicate is derived from lds; a frame-decode task gets the whole frame's RLE), up to 1,408 bytes;
  • a slice — [lo, hi), the piece of the work space this chunk owns. In a vm job the slice is byte offsets of the input; in a frame job it is pixel indices of the frame. Ask the VM where you are with lds;
  • an output buffer — 260 bytes per chunk. emit appends bytes; the coordinator keeps every chunk's output and the WebUI can reassemble them (that is how ESP On Demand gets frames back).

Everything else is a 16-register machine: no floats, no pointers, no host calls. The same code and the same input produce the same result on every chip — that determinism is what makes cluster answers trustworthy.

3. Instruction set

One instruction = 4 bytes: opcode, a, b, c. Jumps take a signed 16-bit instruction offset in b|c<<8 — but you never compute those by hand; vbasm labels do it.

Comparison idiom. cmp yields −1/0/+1, so "jump if less-than" is written as:

  cmp   r5, r0, r2       # r5 = (r0 < r2) ? -1 : (r0 == r2) ? 0 : 1
  add   r5, r5, 1        # 0 only when r0 < r2
  jnz   r5, not_less

Equality alone is just cmp + jz.

Immediates in ALU ops. The ISA takes registers only; vbasm silently materializes add r3, r3, 1 as loadi r7, 1; add r3, r3, r7. That is why r7 is reserved as assembler scratch — never keep a live value there.

## Don't want to learn assembly? Write tasks in ESPlab's own small language instead — variables, `if`, `while`, `for i in 0..99`, `input[i]` to read the chunk's input, `emit x` to write output. It compiles to the same bytecode: ```bash python3 tools/espc.py examples/eod_decode.epl -o task.bin ``` The full video decoder, in the friendly language ([examples/eod_decode.epl](https://github.com/ESPlab-labs/ESPlab/blob/main/examples/eod_decode.epl)): ```python var cur = 0 # absolute pixel cursor var p = 16 # pair cursor into the input while (cur < hi) { cnt = input[p]; p = p + 1 idx = input[p]; p = p + 1 run = (cnt >> 1) + 1 vis = min(cur + run, hi) - max(lo, cur) if (vis > 0) { emitn idx, vis } cur = cur + run } ``` `lo`/`hi` are this chunk's slice of the job — the cluster splits the work; the task just does its part. The assembler (`vbasm`) remains available for hand-tuning hot loops: the assembly version of the same decoder runs ~2.3x fewer instructions.

4. A worked example: count the 'a's

The VM's "hello world" (from examples/count_a.s): each chunk counts the 'a' bytes in its slice and emits the count as a 4-byte little-endian value; the coordinator sums the chunks into the job's aggregate.

# count the 'a' bytes in this chunk's input slice
  lds   r0, 0            # r0 = slice lo (where my input slice starts)
  lds   r1, 1            # r1 = slice hi (where it ends)
  loadi r2, 'a'
  loadi r3, 0
loop:
  cmp  r4, r0, r1        # r4 = (r0 < slice_hi)?
  jz   r4, done
  ldv  r5, r0            # r5 = input[r0]
  cmp  r6, r5, r2
  jnz  r6, skip
  add  r3, r3, 1
skip:
  add  r0, r0, 1
  jmp  loop
done:
  emit r3                # count byte 0 (LSB)
  shr  r4, r3, 8
  emit r4                # byte 1
  shr  r4, r3, 16
  emit r4                # byte 2
  shr  r4, r3, 24
  emit r4                # byte 3 (MSB)
  halt

Submit it and the cluster does the rest:

submit vm <hexcode> <hexinput> <nchunks>    # from any console, any board
jobs                                        # watch it run
job <id>                                    # per-chunk detail

5. The sandbox

Tasks are untrusted by construction:

  • No memory escape — ldv is bounds-checked against the real input length; ld/st are bounds-checked against the 3 scratch slots; jump targets are checked against code length. There are no pointers in the ISA at all.
  • Bounded time — 5,000 instructions per timeslice, 40 slices, then the task is killed with a fault and the chunk fails. A task that never halts costs the cluster 200k instructions, once.
  • Bounded output — the output buffer is fixed at 260 bytes per chunk.
  • Determinism — no clocks, no randomness, no floats: chunk c of a job produces identical bytes no matter which board ran it. That is what lets the cluster re-run a chunk on another board after one asking anyone.

6. Real example: ESP On Demand's decoder

The video service submits each frame of a clip as a frame job: the coordinator slices the frame's pixels into 12 horizontal bands ([lo,hi) = pixel indices), and this task — 34 instructions — decodes a whole band, scanning the frame's run-length coding and emitting only its own pixels:

  lds   r6, 0            # r6 = lo = first pixel of my band
  lds   r2, 1            # r2 = hi = one past my last pixel
  loadi r0, 0            # ABSOLUTE pixel cursor (runs can straddle bands)
  loadi r1, 16           # pairs start at input[16]
scan:
  cmp   r5, r0, r2       # whole band decoded?
  add   r5, r5, 1
  jnz   r5, done
  ldv   r5, r1           # r5 = cnt byte
  add   r1, r1, 1
  ldv   r4, r1           # r4 = palette index
  add   r1, r1, 1        # r1 = next pair
  shr   r3, r5, 1
  add   r3, r3, 1        # r3 = run length
emit_loop:
  cmp   r5, r0, r2       # pixel cursor past my band?
  add   r5, r5, 1
  jnz   r5, next_pair
  cmp   r5, r0, r6       # pixel cursor before my band?
  add   r5, r5, 1
  jz    r5, skip_pix     # pre-band: walk the run without emitting
  emit  r4
skip_pix:
  add   r0, r0, 1
  sub   r3, r3, 1
  jnz   r3, emit_loop
next_pair:
  jmp   scan
done:
  halt

Two lessons are baked into that program, both learned the hard way:

  • The cursor is absolute. A run can straddle your band's start; starting the cursor at lo shifts every run boundary after it and corrupts the band. Walk from 0, emit only what's yours.
  • Pair cursors advance by exactly 2. The read of the count byte and the index byte each advance once — a stray extra add reads the next pair's bytes as data and faults bands that reach the end of input.

7. Assembling: vbasm

./build/vbasm examples/eod_decode.s -o eod_decode.bin
# eod_decode.bin: 34 instructions, 136 bytes

vbasm gives you label: definitions and label-resolved branches (forward references included), 'c' character literals, decimal/hex immediates, and comments with # or ;. Hand-computing jump offsets is exactly how the first decoder got an infinite loop — use the labels.

8. Debugging a task

  • job <id> from any console: chunk states, attempts, output size, duration.
  • jobdump <id>: every chunk's raw output bytes in hex — diff against what you expected.
  • tools/eod_bandtest (build with make build/eod_bandtest): runs your task against every band of a frame on the host, printing per-band status and output. Loop on your laptop, not on the cluster.
  • core/tests/vmdebug: single-step tracing for pure-VM problems (jump math, register lifecycle).
